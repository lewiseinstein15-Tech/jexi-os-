## 1. What is harness engineering

The cleanest definition in the literature is LangChain's identity:

> Agent = Model + Harness. If you're not the model, you're the harness.
> — [The Anatomy of an Agent Harness](https://blog.langchain.com/the-anatomy-of-an-agent-harness/) (LangChain, accessed 2026-09-19)

A harness is every piece of code, configuration, and execution logic around
the model: system prompts, tool and skill definitions, MCP servers, the
filesystem and sandbox it runs in, orchestration and handoff logic, hooks and
middleware for deterministic steps (compaction, continuation, lint checks)
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).

**Harness engineering** is the discipline of designing that wrapper
deliberately instead of accumulating it by accident. Birgitta Böckeler
(Thoughtworks, publishing on Martin Fowler's site) frames it for coding-agent
users as building an *outer harness* of **guides** (feedforward controls that
steer the agent before it acts — rules, skills, templates, codemods) and
**sensors** (feedback controls that let the agent self-correct after it acts —
tests, linters with actionable messages, review agents, logs), where each
control is either **computational** (deterministic, fast: linters, type
checkers, structural tests) or **inferential** (LLM-based semantic judgment)
([Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html),
B. Böckeler, martinfowler.com, 02 Apr 2026, accessed 2026-09-19). An earlier
memo in the same Exploring Gen AI series categorized the practice into
context engineering, architectural constraints, and entropy management
("garbage collection" against drift)
([SECONDARY SOURCE — verify](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html) —
memo URL and three-part framing corroborated by
[walkinglabs/awesome-harness-engineering](https://github.com/walkinglabs/awesome-harness-engineering)
and [prg.sh notes](https://prg.sh/notes/Harness-Engineering), not read at
source this pass).

OpenAI's harness team arrived at the same place from practice: when the only
way to make progress is through the agent, every failure becomes a harness
gap, and the engineering job shifts from writing code to "design
environments, specify intent, and build feedback loops"
([Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/),
OpenAI, 11 Feb 2026, accessed 2026-09-19).

Two boundary clarifications the sources agree on:

- **Harness ≠ framework.** A framework (LangGraph, AutoGen, CrewAI) ships
  primitives; a harness is the integrated runtime actually wrapped around a
  model in production — including the parts frameworks don't give you:
  sandbox policy, identity boundaries, cost governors, observability
  ([SECONDARY SOURCE — verify](https://fountaincity.tech/resources/blog/anatomy-of-an-agent-harness/)).
- **Harness ⊃ context engineering.** Context delivery is one component;
  the harness also owns tools, permissions, verification, memory, task
  execution, and human-in-the-loop design
  ([nxcode guide](https://www.nxcode.io/resources/news/what-is-harness-engineering-complete-guide-2026),
  [SECONDARY SOURCE — verify]).

## 2. Why it matters

The F1-engine-in-a-cheap-car analogy: a frontier model is an F1 power unit.
Drop it into a chassis with no transmission, no cooling, no telemetry — a
cheap car — and it cannot complete a lap. The harness is the chassis,
drivetrain, and pit wall. Upgrading the engine while ignoring the chassis
changes nothing measurable; rebuilding the chassis around the engine
transforms results. The published record backs the analogy:

- **OpenAI** shipped an internal beta product with "0 lines of
  manually-written code" — ~1,000,000 lines across application logic, tests,
  CI, docs, and observability — generated by Codex agents in five months by
  three engineers (~1,500 merged PRs, ~3.5 PRs/engineer/day, throughput
  *increasing* as the team grew to seven). Their explicit diagnosis: early
  progress was slow "not because Codex was incapable, but because the
  environment was underspecified"
  ([OpenAI](https://openai.com/index/harness-engineering/)).
- **Anthropic** found that compaction alone is *not* sufficient: even a
  frontier model on the Claude Agent SDK, looped across context windows with
  only a high-level prompt, fails to build a production-quality app — one-shot
  attempts run out of context mid-feature, and later sessions declare the job
  done prematurely. The fix was harness structure (initializer + coding
  agents, feature lists, progress files), not a better model
  ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents),
  Anthropic, 26 Nov 2025, accessed 2026-09-19).
- **Meta's** Ranking Engineer Agent doubled average model accuracy over
  baseline across six ads ranking models and delivered 5x engineering output
  (three engineers covering a workload that historically needed two engineers
  per model) — an end-to-end harness for the ML experimentation lifecycle,
  not a better optimizer
  ([Engineering at Meta, REA](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/),
  17 Mar 2026, accessed 2026-09-19).
- **Microsoft's** Azure SRE Agent turned traditional hours-long root-cause
  analysis into minutes, and Microsoft's own internal use reached 1,300+
  deployed agents, 35K+ incidents mitigated, 20K+ engineering hours saved,
  with App Service time-to-mitigation down from 40.5 hours to 3 minutes
  ([Introducing Azure SRE Agent](https://techcommunity.microsoft.com/blog/azurepaasblog/introducing-azure-sre-agent/4414569),
  May 2025;
  [GA announcement and Customer Zero posts indexed in microsoft/sre-agent](https://github.com/microsoft/sre-agent),
  accessed 2026-09-19; the 40.5h→3min figure is from Microsoft's own
  customer-zero post — [SECONDARY SOURCE — verify] for the exact baseline
  methodology).
- LangChain reports its coding agent jumped from 52.8% to 66.5% on Terminal
  Bench 2.0 by changing only the harness
  ([SECONDARY SOURCE — verify](https://www.nxcode.io/resources/news/what-is-harness-engineering-complete-guide-2026) —
  figures seen only in third-party coverage, not in the primary LangChain
  post read for this document).

The deepest statement of the "why" is OpenAI's: discipline migrates. Before
agents, engineering discipline lived in the code; with agents it lives in the
scaffolding — tooling, documentation structure, feedback loops, architectural
constraints — that keeps an agent-generated codebase coherent
([OpenAI](https://openai.com/index/harness-engineering/);
framing corroborated by
[alexlavaee's analysis](https://alexlavaee.me/blog/openai-agent-first-codebase-learnings/),
[SECONDARY SOURCE — verify]).

## 3. The pieces of a harness

### 3.1 Agent loop

The base pattern is a ReAct-style loop — reason, act via a tool call,
observe, repeat — owned by the runtime, not the model
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
Because models can only emit text, the loop is what turns emissions into
actions with side effects. Harnesses increasingly give the loop a
general-purpose tool (bash/code execution) so the agent can build its own
sub-tools in code instead of waiting for pre-designed ones
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
OpenAI's variant wraps the loop in self-review: drive a PR through local
review, additional agent reviews, and iteration "until all agent reviewers
are satisfied" — the Ralph Wiggum loop (Ghuntley pattern, linked from
[OpenAI](https://openai.com/index/harness-engineering/);
see also [ghuntley.com/loop](https://ghuntley.com/loop/)).

### 3.2 Planning

Long-horizon work needs an explicit plan artifact the agent cannot quietly
redefine mid-run. Anthropic's initializer agent expands the user prompt into
a machine-checked JSON feature list — 200+ features for a claude.ai clone,
each initially marked `passes: false`, with instructions that it is
unacceptable to remove or edit tests — and the coding agent may only flip
status fields, one feature at a time
([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
OpenAI treats execution plans as first-class versioned artifacts with
progress and decision logs checked into the repository, with ephemeral
lightweight plans for small changes
([OpenAI](https://openai.com/index/harness-engineering/)).
Meta's REA runs a three-phase planning framework (Validation → Combination →
Exploitation) inside engineer-approved compute budgets
([Engineering at Meta](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/)).

### 3.3 Context delivery

OpenAI's rule: "give Codex a map, not a 1,000-page instruction manual." A
giant single AGENTS.md failed in predictable ways — context is scarce, too
much guidance becomes non-guidance, monolithic manuals rot instantly and are
hard to mechanically verify — so they reduced AGENTS.md to a ~100-line table
of contents over a structured, linter-validated `docs/` knowledge base, with
a recurring "doc-gardening" agent opening fix-up PRs against stale docs, and
CI jobs validating structure, cross-links, and freshness
([OpenAI](https://openai.com/index/harness-engineering/)). Skills are the
packaging for progressive disclosure — load a short front-matter entry point,
pull the body only when the skill is selected
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
Anthropic's sessions start with a fixed onboarding sequence — establish the
working directory, read git log and progress files, review the feature list,
run init.sh, smoke-test — so every fresh context window rebuilds state from
artifacts rather than memory
([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents);
onboarding sequence detail corroborated by
[ZenML LLMOps database](https://www.zenml.io/llmops-database/long-running-agent-harness-for-multi-context-software-development),
[SECONDARY SOURCE — verify]).

### 3.4 Tool design

Tools are the harness's API to the world. The LangChain derivation is
behavior-first: want autonomous problem-solving → ship bash + code exec; want
safe execution → sandboxes with allow-lists and network isolation; want
self-verification → ship browsers, log viewers, screenshot tools, test
runners ([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
OpenAI made the *application itself* a tool: bootable per git worktree,
Chrome DevTools Protocol wired into the agent runtime with skills for DOM
snapshots and screenshots, and an ephemeral local observability stack
queryable via LogQL/PromQL — which made prompts like "ensure service startup
completes in under 800ms" tractable
([OpenAI](https://openai.com/index/harness-engineering/)). Boring,
composable, stable dependencies beat clever opaque ones because agents can
model them; OpenAI sometimes preferred reimplementing small helpers over
working around opaque upstream behavior
([OpenAI](https://openai.com/index/harness-engineering/)).

### 3.5 Skills + MCP

Skills are harness-level assets that fight context rot via progressive
disclosure: instead of loading every tool description and manual up front,
the harness loads a catalog and expands one entry on demand
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
MCP (Model Context Protocol) is the emerging standard for connecting tools
and data sources to agents; Microsoft's SRE Agent ships native MCP-backed
connectors for Log Analytics and Application Insights
([microsoft/sre-agent resources index](https://github.com/microsoft/sre-agent),
accessed 2026-09-19), and enterprise platform teams build foreground and
background agents on MCP with RBAC-gated tool surfaces
([SECONDARY SOURCE — verify](https://www.zenml.io/llmops-database) — ZenML
platform-engineering case study entry). Skill collections themselves act as
harnesses in data form: SKILL.md files shape behavior without shipping
runtime code ([SECONDARY SOURCE — verify](
https://agentconn.com/blog/build-agents-run-for-hours-harness-evaluator-handoff-2026/)).

### 3.6 Permissions

Permission design is what bounds the blast radius of a non-deterministic
worker. Anthropic's agents work inside environments the initializer set up,
with strongly-worded file-edit constraints on the feature list
([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
Microsoft's SRE Agent is explicit that the most important controls are
**permission levels and run modes, not prompt quality**, treating the product
as "a governed incident response system, not a conversational assistant with
infrastructure access," with agent hooks (stop hooks, PostToolUse hooks,
global hooks) as governance primitives enforcing approval gates
([Autonomous AKS incident response](https://techcommunity.microsoft.com/blog/appsonazureblog/autonomous-aks-incident-response-with-azure-sre-agent-from-alert-to-verified-rec/4511343)
and [Agent Hooks post, indexed in microsoft/sre-agent](https://github.com/microsoft/sre-agent),
accessed 2026-09-19). Meta's REA works exclusively on the ads ranking
codebase, gets access through preflight checklist reviews, and halts or
pauses when compute thresholds are reached
([Engineering at Meta](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/)).

### 3.7 Memory

The consensus: **progress persists on disk, not in the context window.**
Anthropic's claude-progress.txt plus git history is the cross-session memory;
JSON was chosen for the feature list because models are less likely to
improperly overwrite JSON than Markdown
([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
OpenAI makes the repository the system of record: knowledge that lives in
Google Docs, chat threads, or people's heads is invisible to the agent, so it
gets encoded as versioned in-repo artifacts
([OpenAI](https://openai.com/index/harness-engineering/)). LangChain frames
memory-file standards like AGENTS.md as continual learning by context
injection — the agent edits the file, the harness injects the updated file
into future sessions
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
For very long jobs, Anthropic's follow-up work found summarization-style
compaction insufficient and moved to full context resets with structured
handoff artifacts between sessions
([SECONDARY SOURCE — verify](https://ai-eval.org/post/anthropic-harness-design-for-long-running-application-development) —
summary of "Harness design for long-running application development"; the
primary Anthropic post was not directly readable this pass).

### 3.8 Task runners

Long-running agents need execution substrates: sandboxes that can be created
on demand, fanned out across tasks, and torn down after
([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
OpenAI's runners boot the app per git worktree with an ephemeral
observability stack per task
([OpenAI](https://openai.com/index/harness-engineering/)). Meta's REA is
built on Confucius, Meta's internal agent framework for complex multistep
reasoning, with SDK integrations into job schedulers and experiment tracking,
and a hibernate-and-wake mechanism that serializes agent state when a
multi-day training job launches and restores it on callback
([Engineering at Meta](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/)).
Prime Agent (Prime Intellect) generalizes the pattern for research: a
persistent Python control environment with durable harness state, daemon/
worker/kernel architecture, and background agents with goals, heartbeats, and
schedules ([PrimeIntellect-ai/prime-agent](https://github.com/PrimeIntellect-ai/prime-agent),
MIT, accessed 2026-09-19).

### 3.9 Verification

Verification is the load-bearing piece. OpenAI pushed review toward
agent-to-agent review loops and replaced human QA with mechanical legibility
(bootable app + CDP + logs/metrics), plus custom linters whose error messages
contain remediation instructions so the failure itself teaches the agent
([OpenAI](https://openai.com/index/harness-engineering/)). Anthropic observed
models marking features complete without real testing and responded by making
end-to-end testing an explicit, mandatory step before status flips
([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
Böckeler's sensors taxonomy puts deterministic checks (tests, linters,
structural/architecture tests) on every change, with inferential review on
top ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).
Microsoft's SRE Agent closes the loop with verify-after-remediate:
investigate, fix, then confirm recovery against the original alert signal
([AKS incident response](https://techcommunity.microsoft.com/blog/appsonazureblog/autonomous-aks-incident-response-with-azure-sre-agent-from-alert-to-verified-rec/4511343)).
A known open failure mode: agents are systematically over-generous grading
their own output, especially on subjective quality — hence separate
evaluator roles and rubrics
([SECONDARY SOURCE — verify](https://ai-eval.org/post/anthropic-harness-design-for-long-running-application-development)).

### 3.10 Observability

Observability is what lets anything above work: OpenAI exposed logs, metrics,
and traces to the agent via an ephemeral local stack (Vector → VictoriaLogs/
Metrics/Traces, queried with LogQL/PromQL/TraceQL), explicitly so prompts
could reference real numbers ("no span in these four critical user journeys
exceeds two seconds")
([OpenAI](https://openai.com/index/harness-engineering/)). Microsoft's SRE
Agent runs against Azure Monitor and managed Prometheus signals, merges
alert firings into single incident threads, and posts follow-ups to Teams and
GitHub ([AKS incident response](https://techcommunity.microsoft.com/blog/appsonazureblog/autonomous-aks-incident-response-with-azure-sre-agent-from-alert-to-verified-rec/4511343);
[Azure Monitor integration, indexed in microsoft/sre-agent](https://github.com/microsoft/sre-agent)).
For portability of agent traces across backends, OpenTelemetry's semantic
conventions for generative AI systems are the emerging standard
([walkinglabs list entry](https://github.com/walkinglabs/awesome-harness-engineering),
pointing to the OTel GenAI semconv work).

### 3.11 Human-in-the-loop

The harness decides where scarce human judgment lands. OpenAI's team keeps
humans steering through prompts and optional PR review, having "pushed almost
all review effort towards being handled agent-to-agent," with the stated
scarce resource being "human time and attention"
([OpenAI](https://openai.com/index/harness-engineering/)). Böckeler's
steering loop makes the human's job iterating on the harness itself — every
repeated failure should end as a new guide or sensor, ideally authored by an
agent ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).
Meta keeps engineers at strategic decision points: budgets approved up
front, oversight of hypothesis direction
([Engineering at Meta](https://engineering.fb.com/2026/03/17/developer-tools/ranking-engineer-agent-rea-autonomous-ai-system-accelerating-meta-ads-ranking-innovation/)).
Microsoft's SRE Agent performs operations "on behalf of and with approval of
the user" ([Introducing Azure SRE Agent](https://techcommunity.microsoft.com/blog/azurepaasblog/introducing-azure-sre-agent/4414569)).

## 5. Anti-patterns

1. **The 1,000-page AGENTS.md.** One giant instruction file crowds out task
   and code, turns importance into noise, rots instantly, and resists
   mechanical verification. OpenAI's fix: ~100-line map + linter-validated
   docs tree + doc-gardening agent
   ([OpenAI](https://openai.com/index/harness-engineering/)).
2. **Prompt worship.** Iterating on prompts when the failure is harness-shaped
   (missing verifier, missing tool, missing artifact). The agent-side version:
   treating every failure as "try harder" instead of "what capability is
   missing, and how do we make it legible and enforceable"
   ([OpenAI](https://openai.com/index/harness-engineering/);
   [Skill Issue: Harness Engineering for Coding Agents](https://github.com/walkinglabs/awesome-harness-engineering) —
   indexed argument that weak coding-agent results are usually harness
   problems).
3. **Feedback-only or feedforward-only.** Rules without sensors produce an
   agent that never learns it violated them; sensors without rules produce an
   agent that repeats the same mistakes
   ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).
4. **Self-grading as the only verifier.** A model grading its own work
   returns over-generous verdicts that compound over long runs; verification
   needs independence (separate evaluator roles, rubrics, or deterministic
   checks) ([SECONDARY SOURCE — verify](
   https://ai-eval.org/post/anthropic-harness-design-for-long-running-application-development)).
5. **Context hoarding.** Holding everything in the window instead of
   persisting progress to disk artifacts; the direct cause of one-shotting,
   half-implemented features, and premature "done"
   ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
6. **Premature completion / moving goalposts.** Without an external,
   machine-checked definition of done, later sessions survey partial progress
   and declare victory. The feature list exists precisely to prevent this
   ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
7. **Permission sprawl.** Granting broad standing access instead of scoped,
   auditable permission levels and run modes; Microsoft's field guidance is
   that governance quality is decided there, not in prompt quality
   ([AKS incident response](https://techcommunity.microsoft.com/blog/appsonazureblog/autonomous-aks-incident-response-with-azure-sre-agent-from-alert-to-verified-rec/4511343)).
8. **Retrofit-only harnessing.** Böckeler's caution that harnessing an
   existing unstructured codebase is like running a static analyzer for the
   first time on an unchecked codebase — most effective when designed in from
   the start ([SECONDARY SOURCE — verify](
   https://github.com/robyscar/ML_LLM_CLAUDE_SKILLS_Jamie-BitFlight_claude_skills/blob/main/research/evaluation-testing/harness-engineering-martin-fowler.md) —
   reading-notes summary of the Exploring Gen AI memo).
9. **Harness theater.** Adding configuration, gates, and dashboards for
   their own sake. Böckeler's guidance: start simple, add controls only when
   failures force them, and treat harness changes like code — iterate and
   discard what does not help ([SECONDARY SOURCE — verify](
   https://prg.sh/notes/Harness-Engineering)).
10. **Confusing the framework with the harness.** Buying a framework and
    believing sandbox policy, identity, cost governance, and observability
    come with it ([SECONDARY SOURCE — verify](
    https://fountaincity.tech/resources/blog/anatomy-of-an-agent-harness/)).

## 6. How JEXI applies each piece

JEXI is a single-operator, local-first agent OS. The mapping below cites the
repository's own evidence (paths and commits on branch `phase-17-arena`).

- **Agent loop** — the console server's event loop dispatches commands
  through a graph-first registry (`server/src/services/*`, Phase 11:
  graph-first dispatch with `NOT_IN_GRAPH` honesty, gated dispatch); the
  browser runtime (Scope C, commit `d2c50c8`) gives agents a real CDP session
  — the same "wire Chrome DevTools into the runtime" move OpenAI made
  ([OpenAI](https://openai.com/index/harness-engineering/)).
- **Planning** — session memory blocks (Current State / immediate next steps)
  function as the versioned plan artifact; phase scopes are external plans
  with acceptance criteria the executor cannot quietly redefine — the same
  shape as Anthropic's feature list
  ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Context delivery** — `AGENTS.md` is shared and read-only; skills load via
  progressive disclosure (`catalog.js` line-based front-matter; SkillLoop
  recall); the viking context sidecar (Scope E, `7d2b408`) stores per-directory
  metadata (`<dir>/.viking/meta.json`) with deterministic token estimation
  (`ceil(chars/4)`) — repo-local artifacts as the system of record, per
  [OpenAI](https://openai.com/index/harness-engineering/).
- **Tool design** — every capability ships as a real, runnable CLI or module
  (`scripts/phase17-*.mjs`, `render-diagram.mjs`), with honest error codes
  (`E_UNKNOWN_TYPE`, `E_SPEC_MISSING`) — remediation-shaped messages, per the
  linter-message practice in [OpenAI](https://openai.com/index/harness-engineering/).
- **Skills + MCP** — `skills/library/scientific` (166 skills, Scope F,
  `44c9708`), `skills/library/security` (818 skills + framework indices,
  Scope G, `9c932ab`), authored skills (`skills/design/diagram-design`,
  Scope H, `aa85037`); MCP registry union of 53 servers (Phase 11).
- **Permissions** — zone-guarded scopes (explicit allowed paths per scope,
  probe-enforced via `git status` checks, e.g. P12 in Scope H), NEVER-TOUCH
  lists for shared surfaces (`server/index.js`, `events/hud/**`,
  `commands/registry.js`), and a Prompt Defense Baseline block lint-enforced
  in every skill — the permission-levels-and-modes principle from Microsoft's
  SRE Agent ([AKS post](https://techcommunity.microsoft.com/blog/appsonazureblog/autonomous-aks-incident-response-with-azure-sre-agent-from-alert-to-verified-rec/4511343)),
  applied to a single-repo workforce.
- **Memory** — `memory/` with aging/reinforcement semantics (Scope D,
  `65ce29`: reinforcement resets the aging clock), plus the standing session
  memory protocol: state persists in structured blocks between turns, not in
  any window — Anthropic's progress-file pattern
  ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Task runners** — background process management for dev servers and long
  jobs, probe scripts as batch task runners, CI on branch for external
  verification.
- **Verification** — probe-first acceptance: every scope ships a numbered
  probe (P1–P14 pattern) whose raw output is the acceptance evidence;
  determinism is hash-checked (sha256-identical renders, Scope H P5);
  byte-identity is verified against history before acceptance (Scope H
  verification: 40/42 files hash-matched). This is Böckeler's computational
  sensor layer ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).
- **Observability** — HUD event stream (`events/hud/**`), raw-output-only
  probe logs, push verification via `git ls-remote` SHA comparison after
  every scope, honest NOT VERIFIED markers where the sandbox cannot verify
  (e.g. no rasterizer for SVG→PNG).
- **Human-in-the-loop** — the STOP-and-wait protocol: one commit per scope,
  push, report, stop; merge decisions belong to the owner only, on explicit
  merge prompts; a second model (GLM) cross-verifies after merge —
  independence of verifier and builder, per anti-pattern #4.

## 7. Where JEXI diverges and why

1. **Single-operator, no enterprise RBAC.** Microsoft's SRE Agent governs a
   fleet; JEXI governs one repository for one owner. Zone guards and
   NEVER-TOUCH lists replace identity infrastructure — same principle
   (bound blast radius), proportionate mechanism.
2. **Probes are the acceptance contract, not CI dashboards.** Enterprise
   harnesses converge on hosted observability; JEXI converges on numbered
   probes with raw pasted output at report time. Rationale: evidence must be
   readable by the operator and the cross-verifier without infrastructure,
   and unfakeable (raw output only, synthetic data labeled).
3. **Determinism over LLM-as-judge in deliverables.** Where other harnesses
   add inferential review of artifacts (diagrams, documents), JEXI renders
   deterministic output (same spec → same bytes, hash-verified) and reserves
   LLM judgment for cross-verification of process, not artifact aesthetics.
   Rationale: hashable artifacts make verification computational, which is
   the cheaper and more reliable sensor class
   ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)).
4. **Honesty primitives as first-class output.** `NOT VERIFIED` markers,
   `E_*` error codes, "synthetic session" labels, and honest counts in commit
   subjects are enforced conventions, not style choices. The harness treats
   an unverifiable claim as a defect — the discipline version of OpenAI's
   "no manually-written code" constraint
   ([OpenAI](https://openai.com/index/harness-engineering/)).
5. **Dual-verifier instead of agent-to-agent review at scale.** OpenAI pushed
   review to agent-to-agent loops ([OpenAI](https://openai.com/index/harness-engineering/));
   JEXI runs a builder (arena) and an independent cross-verifier (GLM) with
   the owner as merge authority — a two-party trust chain sized to a
   single-operator project.
6. **File-and-git memory only.** No vector store in the hot path; memory is
   files, git history, and sidecar metadata with deterministic estimates.
   Rationale: inspectability and hashability beat retrieval sophistication
   at this corpus size (LangChain notes the filesystem is the natural
   collaboration surface —
   [LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)).
7. **Verbatim preservation of acquired skill canon.** Ported skills keep
   upstream references byte-identical (verified by hash in Scope H), with
   JEXI-specific behavior added *beside* the canon, not edited into it —
   provenance is part of the harness.

## 8. Open problems

- **Self-evaluation reliability.** Over-generous self-grading on subjective
  output remains unsolved in general; rubrics and adversarial evaluators are
  mitigations, not fixes ([SECONDARY SOURCE — verify](
  https://ai-eval.org/post/anthropic-harness-design-for-long-running-application-development);
  [Milvus on agents grading their own work](https://milvus.io/blog/harness-engineering-ai-agents.md),
  [SECONDARY SOURCE — verify]).
- **Context-rot economics.** Progressive disclosure, compaction, resets, and
  condensation all trade tokens for fidelity; no published model sets the
  exchange rate ([LangChain](https://blog.langchain.com/the-anatomy-of-an-agent-harness/);
  [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Multi-agent shared state.** Many harnessed agents sharing one codebase /
  one commons lacks settled conventions for ownership and conflict
  ([Many Hands Engineering, indexed in walkinglabs list](
  https://github.com/walkinglabs/awesome-harness-engineering),
  [SECONDARY SOURCE — verify]; LangChain names orchestrating hundreds of
  parallel agents an open frontier).
- **Harness measurement and reporting standards.** Structured reporting of
  harness design (e.g. the proposed HarnessCard / control–agency–runtime
  decomposition) is a research position, not a standard
  ([SECONDARY SOURCE — verify](https://github.com/walkinglabs/awesome-harness-engineering) —
  position-paper index entry).
- **Trace portability.** OTel GenAI semantic conventions are young; portable
  agent traces across observability backends remain aspirational
  ([walkinglabs index](https://github.com/walkinglabs/awesome-harness-engineering)).
- **Cost governance.** Runaway token spend is listed as a first-class harness
  component by practitioners, but few public harnesses ship pre-flight
  circuit breakers as standard
  ([SECONDARY SOURCE — verify](https://fountaincity.tech/resources/blog/anatomy-of-an-agent-harness/)).
- **The agent security surface.** Local tool exposure is an unsolved boundary
  problem: an agent runtime that binds services to `0.0.0.0` turns a helpful
  loop into a network-accessible execution oracle. JEXI's own Scope J
  (Ollama exposure detection, localhost-by-default) is a live instance of
  this open problem.
- **Harness drift.** Guides and sensors rot with the code they observe;
  OpenAI's doc-gardening agent is a partial answer, and continuous
  "garbage collection" of harness debt remains an open engineering problem
  ([OpenAI](https://openai.com/index/harness-engineering/);
  [SECONDARY SOURCE — verify](https://prg.sh/notes/Harness-Engineering) for
  the entropy-management framing).
